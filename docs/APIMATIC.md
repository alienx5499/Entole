# APIMatic build log

Entole moves money through PayPal in one file: `packages/mandate/src/infrastructure/paypal/paypal-gateway.ts`. Every Orders and Payments call in that file goes through `@paypal/paypal-server-sdk`, the PayPal Server SDK that APIMatic generates. I wrote it with an AI coding assistant that had the APIMatic Context Plugin for PayPal installed. This page lists what I used, where it lives, what got in my way, and what I would ask APIMatic for.

## Setup

| What | Value |
| --- | --- |
| SDK | `@paypal/paypal-server-sdk` `2.5.0`, pinned in `packages/mandate/package.json` (the latest npm release) |
| Generator | APIMatic v3.0. Every SDK source file says "automatically generated by APIMATIC v3.0" in its header |
| Context Plugin | `paypal@context-plugins` `0.4.1`, installed with `npx context-plugins install paypal` |
| Plugin skills I used | the nine `typescript-*` skills: getting-started, integrate-paypal, client-initialization, authentication, calling-endpoints, models, error-handling, configuration-resilience, testing |

I installed the plugin before the PayPal gateway went into the repo. A first local draft used plain `fetch` calls with hand-built URLs and my own OAuth helper; I dropped it and wrote the gateway on the SDK instead. Plain HTTP is left only where the SDK has no endpoint (see "Still raw HTTP" below).

## Calls I make through the SDK

Line numbers are in `packages/mandate/src/infrastructure/paypal/paypal-gateway.ts`.

| Entole step | SDK call | Line | Idempotency key (`paypalRequestId`) |
| --- | --- | --- | --- |
| Shopper signs a limit order | `OrdersController.createOrder` with `CheckoutPaymentIntent.Authorize` | 76 | `order-<mandateId>` |
| PayPal sends the buyer back | `OrdersController.getOrder` (status, amount, `custom_id`) | 135 | none, a read |
| Approval matches, take the hold | `OrdersController.authorizeOrder` | 151 | `authorize-<orderId>` |
| Price drops under the limit | `PaymentsController.captureAuthorizedPayment` (partial or final) | 182 | from the caller, see below |
| Shopper asks for money back | `PaymentsController.refundCapturedPayment` (full refund, no body) | 216 | `refund-<mandateId>` |
| Order closes or expires | `PaymentsController.voidPayment` | 228 | `void-<authorizationId>` |
| Hold nears its expiry | `PaymentsController.reauthorizePayment` | 247 | `reauthorize-<authorizationId>` |

Before taking the hold, `fundMandate` reads the order back with `getOrder` and refuses unless it is `APPROVED`, its amount and currency equal the signed budget, and its `custom_id` equals the mandate digest (`checkApproval` in `packages/mandate/src/domain/transitions.ts`), so the approval PayPal returns is checked against the signed terms before any money is held.

The capture key comes from `packages/mandate/src/application/propose-order.ts:82`. A limit order captures once, so the key is `<mandateId>-capture`, and a retry after a timeout replays the first capture instead of charging twice.

SDK models and enums I build or read:

- `CheckoutPaymentIntent.Authorize` (line 79), so the order is a hold, not a charge.
- `ItemCategory.PhysicalGoods` (line 92) on a single line item, with `amount.breakdown.itemTotal` (line 98), so the approval page shows the signed terms.
- `PaypalExperienceUserAction.Continue` (line 107) and `PaypalWalletContextShippingPreference.GetFromFile` (line 109), so the buyer picks a ship-to address inside PayPal.
- `softDescriptor`, `brandName`, `locale`, `returnUrl`, `cancelUrl` and `orderUpdateCallbackConfig` (`CallbackEvents.ShippingAddress`) on the order body (lines 85 to 121).
- On authorize: `purchaseUnits[0].payments.authorizations[0]` for id, amount and `expirationTime`, and `purchaseUnits[0].shipping` for the address (lines 153 to 174).
- On capture: `finalCapture`, `invoiceId`, `noteToPayer` in the body (lines 187 to 189), then `status`, `sellerProtection.status` and `sellerReceivableBreakdown.paypalFee` / `netAmount` from the answer (lines 201 to 209).

## Building on Entole: my own SDK and context plugin

I also used APIMatic in the other direction. The bearer-token part of Entole's own API is described in [`docs/openapi.yaml`](openapi.yaml) (7 operations, with a drift test in `apps/api/test/openapi.test.ts` that calls each one and checks the response against the spec). From that spec APIMatic generated:

- **An Entole TypeScript SDK**, generated with the APIMatic CLI (code generator v4) from the final spec and kept unedited in [`packages/entole-sdk`](../packages/entole-sdk). Entole's MCP server (`apps/mcp/src/client.ts`) now makes every call to Entole through it, so an AI client that drafts a limit order goes MCP server, Entole SDK, Entole API. The SDK sends an `Idempotency-Key` on every non-GET call, and the Entole API honours it: a retried `POST /api/mandates`, close or schedule proposal with the same key returns the first answer instead of running twice (the answer is kept for 24 hours, and a running request holds its key for 5 minutes). The header is declared in `docs/openapi.yaml`.
- **An Entole context plugin**, in [`context-plugin/`](../context-plugin), with the SDK bundled and ten skills, so another developer's coding assistant can integrate Entole from the real contract. Install it with `npx context-plugins install ./context-plugin`.

Both are attached to the [v1.0.0 release](https://github.com/alienx5499/Entole/releases/tag/v1.0.0) as an npm tarball and a zip, with checksums.

APIMatic's first score for the spec was 70 out of 100 (SDK generation 100, documentation 87, AI tools 85). I fixed every lint finding it reported: descriptions on every schema and field, examples that validate against their schemas, and named models instead of inline ones. Generating the SDK also caught two real spec bugs, which I fixed in the spec rather than in code: two always-true and always-false flags declared as constants decoded as strings, and a 409 on cancel that the route can never return.

## Before and after: one capture

My first draft was never committed, so the first snippet is the equivalent raw call, not a copy of it. It is what every PayPal call looks like without the SDK.

Raw HTTP (what the SDK replaced):

```ts
const token = await getAccessToken(); // my own OAuth client-credentials helper, with its own cache and expiry
const res = await fetch(
  `${PAYPAL_API_BASE}/v2/payments/authorizations/${authorizationId}/capture`,
  {
    method: "POST",
    headers: {
      Authorization: `Bearer ${token}`,
      "Content-Type": "application/json",
      "PayPal-Request-Id": idempotencyKey,
    },
    body: JSON.stringify({
      amount: { currency_code: "USD", value: "326.99" },
      final_capture: true,
      invoice_id: invoiceId,
      note_to_payer: note,
    }),
  },
);
if (!res.ok) throw new Error(`capture failed: ${res.status} ${await res.text()}`);
const capture = (await res.json()) as any; // untyped: a misspelled field is only found at runtime
```

With the SDK (`packages/mandate/src/infrastructure/paypal/paypal-gateway.ts`):

```ts
const { result } = await this.payments.captureAuthorizedPayment({
  authorizationId,
  paypalRequestId: idempotencyKey,
  body: {
    amount: { currencyCode: "USD", value: formatUsd(amount) },
    finalCapture: true,
    invoiceId,
    noteToPayer: note,
  },
});
// result is a typed Capture: status, sellerProtection, sellerReceivableBreakdown
```

The SDK owns the token, the URL, the snake_case body and the error type. The request id header became a named field (`paypalRequestId`), so a capture without one stands out in review, and a wrong field name fails `tsc` instead of failing at PayPal.

## Client setup

The client is built once in the gateway constructor (lines 53 to 72):

- `Environment.Sandbox` or `Environment.Production`, picked from `PAYPAL_API_BASE` through a two-entry map (lines 22 to 25). An unknown base URL throws at startup instead of falling back to sandbox.
- `clientCredentialsAuthCredentials` with an `oAuthTokenProvider` (line 64). The provider shares one cached token between the SDK and my one raw HTTP call, and concurrent callers share one in-flight token request (`accessToken()`). It uses the SDK's own `clientCredentialsAuthManager.fetchToken()` and `isExpired()`.
- `timeout: 15000`, so a hung PayPal call cannot hold a mandate lock forever.
- `retryConfig: { maxNumberOfRetries: 0 }`. SDK retries are off. Every write already sends a stable key, so turning them on would be safe; I have not done it yet.
- `unstable_httpClientOptions: { adapter: "fetch", env: { fetch } }`, so an injected `fetch` sees every SDK request. My tests depend on this.

## Errors

One wrapper, `sdk()` near the end of the file, catches the SDK's `ApiError` and turns it into my own `PayPalError` with the HTTP status, PayPal's `debug_id` and the list of `details[].issue` codes. The token request goes through the same wrapper. Code above the gateway never imports anything from the SDK.

Three places read those issue codes:

- `voidAuthorization` (lines 225 to 240) treats a 422 with `VOIDED` or `EXPIRED` as success, since Close only needs the hold to be gone.
- `reauthorize` (from line 242) treats 422 `REAUTHORIZATION_TOO_SOON` as a timing slip and throws so the next tick retries; any other 422 is a final "denied".
- The API answers any `PayPalError` with `502 upstream_error` (`apps/api/src/http/http.ts:89`). The error message never carries the client id or secret; a test checks that.

## Still raw HTTP

- Webhook and order callback signatures are no longer an HTTP call at all: `paypal-signature.ts` checks them locally against PayPal's cert, which PayPal's webhook guide now calls the preferred method. The SDK has no helper for either.
- Log in with PayPal, in `packages/identity/src/infrastructure/paypal/paypal-identity.ts:54` and `:67`. The SDK has no userinfo endpoint, and its token manager handles client credentials, not the `authorization_code` exchange.

## What the types did for me

What the code shows, without overstating it:

- Request bodies are typed models, so field names are camelCase TypeScript (`purchaseUnits`, `unitAmount`, `experienceContext`) and the SDK maps them to PayPal's snake_case JSON. I never hand-write a JSON key for an Orders or Payments call.
- Enum members replace string literals for intent, item category, user action and shipping preference. A typo is a compile error, not a 422 from PayPal.
- Every field in a response is optional in the types. That is why each method checks what it needs and throws a named error when it is missing (lines 129, 137, 156, 200, 221, 253) instead of trusting `result.id!`.
- `ApiError.body` is typed `string | Blob | ReadableStream`, which is why `sdk()` checks `typeof e.body === "string"` before parsing.

## Gaps I hit

1. **Enum types are looser at runtime than at compile time.** Response enums are built with `stringEnum(X, true)`, which lets any string through. `result.status` is typed `CaptureStatus`, but a new status from PayPal arrives as a plain string anyway. My port types status as `"COMPLETED" | "PENDING" | "DECLINED" | "FAILED" | string`, and I pass it through `String()` (lines 204 and 206, and the `DENIED` check in `reauthorize`) to make clear I store text, not a closed enum.
2. **No base URL option.** Version 2.5.0 picks the host from `Environment` only, so I map my `PAYPAL_API_BASE` onto one of two enum members (the map at line 22).
3. **The plugin and the npm SDK describe different packages.** The plugin's TypeScript skills document a newer generated SDK, `paypal` 2.29.0 with `PaypalClient`, built from GitHub and not on npm. It ships an SDK map (`sdk-map.md` and `map/operations/`). The npm package I use has `Client` plus controllers and no SDK map, so I read the generated `src/` for exact names. The general patterns in the skills (idempotency keys, token handling, error narrowing, tests with an injected fetch) still applied.
4. **Log in with PayPal and webhook signatures are outside the SDK.** The two identity calls (code exchange and userinfo) still build URLs and headers by hand, and webhook signatures are checked in my own code.
5. **The fetch adapter is `unstable_`.** I rely on it for tests, and the name tells me it may change.

## Tests

`packages/mandate/test/infrastructure/paypal-gateway.test.ts` has 11 tests that run the real SDK against a stubbed `fetch`. The stub records each request the SDK sends and answers per route. They cover the order body and the `payer-action` link, authorize with and without a ship-to address, partial and final capture with the idempotency key as `PayPal-Request-Id`, full refund, void reusing the cached token, void on 422 `VOIDED`/`EXPIRED`, other 422s, the ship-to callback config, and that no secret leaks into an error message. Webhook signatures are checked locally and tested in `paypal-signature.test.ts`.

`packages/mandate/test/infrastructure/paypal.live.test.ts` runs against the PayPal sandbox with `LIVE=1`: create, a human approves as the sandbox buyer, two partial captures on one authorization, then void.

## What I would ask APIMatic for

1. Publish the plugin's SDK (`paypal` 2.29.0) to npm, or point the plugin at `@paypal/paypal-server-sdk`, so the skills match what `npm install` gives you.
2. Ship `sdk-map.md` inside `@paypal/paypal-server-sdk` too. It is the part of the plugin I wanted most and could not use.
3. Add `userinfo` to the generated SDK, and a signature helper for webhooks and the order update callback that takes the raw body.
4. A typed `ApiError` helper for PayPal's error body (`debug_id`, `details[].issue`), so every project stops writing the same parser.
5. Either closed enums in response types or an explicit `| string` in the type when unknown values are allowed.
6. A `baseUrl` override in `@paypal/paypal-server-sdk` for proxies and recorded test servers.
